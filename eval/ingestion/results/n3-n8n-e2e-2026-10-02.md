## Preparación operacional

El workflow almacenado en N8N permaneció `active=false`; se inició manualmente. Los
nodos HTTP usaron credencial local HTTP Header Auth, sin registrar su token ni ID
interno. Configuración observada: `Check Ingestion Status` timeout 30000 ms,
`Execute Ingestion` 900000 ms y `Reconcile Status` 30000 ms; los tres con
`retryOnFail=false` y `onError=continueErrorOutput`.

El JSON versionado conserva placeholders para `ingestion_base_url`, `workflow_ref` y
el ID de credencial portable (`__RELINK_AFTER_IMPORT__`). La instancia recibió
overrides locales. `workflow_ref` identifica la definición base usada, pero no se
afirma que el objeto almacenado internamente por N8N fuera byte-for-byte idéntico al
JSON versionado después de esos overrides.

## Incidencias previas a la ejecución exitosa

### Backend anterior en el puerto local

Al inicio seguía escuchando en `127.0.0.1:3010` un backend con otro `workflow_ref`.
Una consulta `/status` con el `workflow_ref` de N3 respondió HTTP 409,
`CONTROL_REJECTED`, `reason=workflow_mismatch`. Se identificó y cerró el proceso
anterior y se inició `backend/rag` con la referencia de N3. Esto fue un mismatch de
configuración del proceso activo, no un fallo del pipeline de ingesta.

### Referencia de credencial después de importar

La copia importada conservó el ID placeholder `__RELINK_AFTER_IMPORT__`, aunque
existía una credencial local Header Auth. El primer intento del workflow acabó en la
salida de error de `Check Ingestion Status` con el mensaje saneado:
`Credential with ID "__RELINK_AFTER_IMPORT__" does not exist for type "httpHeaderAuth".`
`/execute` no fue alcanzado; no se inició ingesta ni hubo escrituras atribuibles a
ese intento. Se revincularon operacionalmente los tres nodos HTTP a la credencial
local; después, `Check Ingestion Status` devolvió `not_started`. No se registra el
token, Authorization header ni ID interno real de la credencial.

`/execute`. Su resumen fue:

- `workflow_result`: `execute_response_received`.
- `action_taken`: `execute_once`.

- `release_id`: `02085c98-8913-4ded-ae00-d5f0c64bda86`.

En `Execution Summary`, `attempt_no`, `recovery_required` e `item_counts` fueron

PostgreSQL confirmó `attempt_no=1`.

`attempt_no=1`, `started_at=2026-10-02 19:56:54.106789+00` y
`finished_at=2026-10-02 19:57:23.745929+00`. `duration_seconds=29.639` es únicamente
la duración del `ingestion_run` persistida por PostgreSQL; no es duración total del
workflow N8N, duración desde Manual Trigger, benchmark, SLA ni métrica general.

## Límites de la evidencia

La evidencia acredita el camino manual exitoso observado:
N8N → HTTP privado → `backend/rag` → Ollama → PostgreSQL → publicación de release,
en Windows + Docker Desktop local. No acredita Linux, servidores futuros,
infraestructura UNAB/CCD, producción ni portabilidad de
`host.docker.internal`; tampoco `scheduled`, retry/recover N8N, la rama real de
timeout/reconciliación, concurrencia N8N, todos los escenarios I01–I24 o todos los
fallos deliberados, rendimiento general, SLA, duración total Manual Trigger →
publicación, métricas OE1/OE2/OE4 por sí solas, calidad RAG, RAGAS, Agent/ReAct, MCP
ni autenticación de usuario final.
