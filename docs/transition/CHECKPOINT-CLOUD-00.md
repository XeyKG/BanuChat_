### Cuatro formas de estado

1. **Embeddings documentales persistentes.** `stageDocuments` inserta texto y metadatos de chunks en PostgreSQL. `generateEmbeddings` actualiza la columna vectorial y registra generación. La publicación comprueba cobertura, dimensión, norma y asociación a la ejecución. Las consultas recuperan filas de la release autorizada con distancia coseno. El respaldo unificado de octubre aporta evidencia histórica de persistencia, con cero embeddings faltantes según su comprobación. La auditoría actual confirmó la implementación por código y revisó esa evidencia histórica.
2. **Vectores de consulta efímeros.** `backend/api/src/application/document-query-retrieval.ts` genera el vector mediante `embedQuery`, lo pasa como parámetro SQL y recibe resultados. El camino MCP sigue el mismo patrón. El flujo inspeccionado carece de una escritura de ese vector.
3. **Memoria conversacional acotada.** `chat/conversation-context.ts` selecciona y limita mensajes previos para resolver referencias y construir la consulta. El contexto se arma en ejecución a partir del historial, con límite de ocho mensajes y 6000 caracteres. La caché web de interfaz tiene su propio ciclo de vida.
4. **Historial durable.** `application/messages.ts` y `auth/resources.ts` usan conversaciones y mensajes de PostgreSQL, con escrituras transaccionales, control de dueño y citas vinculadas a releases. El historial y la sesión requieren preservar su semántica aunque cambie el proveedor de base de datos.

## Reunión del 10 de noviembre

## Incompatibilidades y trabajo por prioridad

### P0 · Separar el destino sintético y demostrar restauración

- El modo unificado actual fuerza `ccd_local` en `start-unified.mts` y `createAuthenticatedRuntimeServer`. `unified-main.ts` exige explícitamente `banuchat-ccd-local` y manifiesto no sintético. El dump unificado incluye CCD, aunque tenga datos auxiliares sintéticos. CLOUD-01 debe arrancar con una base desechable independiente y una lista positiva de esquema, releases y artefactos a partir de `data/synthetic`. Excluir texto CCD, derivados, embeddings, citas, archivos, historial y sesiones del entorno local. Usar cuentas de prueba nuevas. El entorno CCD debe seguir siendo capaz de operar localmente.
- Tratar las migraciones como ramas con precondiciones. `001_initial_schema.sql` es la base. `002–005` dependen de `banuchat_ccd_dev`. `006–008` y `010` validan destino/configuración de autenticación sintética; `009` está ligado a un entorno de prueba nombrado. `011` es el bootstrap CCD y usa `banuchat_ccd_auth_i1b_test`. `012–014` exigen `banuchat_unified` y contienen dependencias del modo unificado/CCD. Diseñar la receta sintética explícita antes de aplicar cambios. Si la demo cloud requiere paridad con la orquestación unificada, incorporar esa composición con datos sintéticos y pruebas propias.
- Repetir respaldo/restauración sobre el origen sintético aislado. Verificar filas, claves, propietarios, grants, funciones, releases activas, dimensiones y resultados de retrieval, conversaciones y citas con fixtures. Comprobar artefactos por hash y ensayar reversión de configuración hacia la referencia local. Ensayar con la versión y roles de destino antes de publicar.

### P2 · MCP en AWS Academy

- Reutilizar el servidor, las seis herramientas y sus validaciones. `runtime.ts` del MCP sintético exige host local y `unified-main.ts` fija host, base y modo CCD. `StdioMcpClientFactory` inicia un proceso local con contexto fijado por el backend. Si se autoriza alojar API y MCP juntos durante la demostración, stdio puede mantenerse. Si API queda local y MCP vive en AWS como servicio independiente, añadir transporte Streamable HTTP y un cliente compatible, autenticación de servicio, transporte privado/TLS, validación de origen cuando corresponda y aislamiento de principal y releases. Evitar aceptar el principal del cliente móvil como autoridad. [Especificación de transportes MCP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).
- Resolver inferencia antes de elegir instancia. `main.ts` del MCP sintético fija Ollama a loopback y `unified-main.ts` también usa el cliente de embeddings de consulta. Los clientes Ollama de API y RAG restringen el host a loopback. Un MCP remoto completo necesita una ruta de inferencia autorizada que preserve modelo, revisión y dimensión. Medir CPU/RAM, latencia y tamaño del modelo antes de cotizar. Mantener Ollama, n8n y API locales en el primer corte de base de datos.
- `backend/api/src/orchestration/n8n-conversation.ts` restringe el webhook a loopback. El workflow conversacional admite o aclara, mientras la ejecución MCP y la persistencia quedan en el backend. Separar hosts exigiría decidir conectividad y credenciales. Restaurar definiciones seleccionadas, volver a vincular credenciales y activar solo los flujos de prueba después de validarlos.

## Respaldo, aislamiento y costos

- `infra/scripts/verify-synthetic-backup.mjs` tiene evidencia registrada en `eval/oe6/results/oe6-backup-restore-2026-10-25.json`: dump sintético, restauración efímera sin red y 16 huellas de tablas coincidentes. Es evidencia del 25 de octubre. El script unificado usa snapshot PostgreSQL de solo lectura, dump custom, huellas de estructura/datos, roles restaurados sin login y contenedores sin red ni puertos.
- `eval/oe6/results/oe6-unified-recovery-2026-10-31.json` registró restauraciones locales de PostgreSQL unificado y OE2 con comparaciones coincidentes. El ejercicio global quedó parcial: 107 artefactos vigentes verificados, 33 referencias históricas no recuperables, ocho conversaciones preexistentes sin dueño, respaldo de definiciones n8n sin restauración operativa, y sin snapshot atómico entre almacenes. No se acreditó inicio de la app restaurada. Esos dumps y sus ubicaciones privadas no son insumos de migración cloud.
- `.gitignore` excluye `infra/local` y el contenido local CCD por defecto, con contratos y guías versionados. `.dockerignore` y el Dockerfile seleccionan el dataset sintético para la imagen backend. Revisar también los mounts, artefactos empaquetados y el contenido efectivo del dump antes de transferir. El destino administrado requiere su propio ensayo lógico con roles y esquemas seleccionados, sin recrear bases o roles administrados del proveedor. [Respaldo lógico y restauración en Supabase](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).
- Supabase Free anuncia 500 MB de base, 5 GB de egreso y pausa tras una semana de inactividad. Pro parte de US$25 al mes. Medir tamaño de tablas, índices, vectores y margen antes de adoptar el plan gratuito. El presupuesto académico indicado de AWS es US$50 y el costo de Supabase se evalúa aparte. [Precios de Supabase](https://supabase.com/pricing).
- AWS requiere región, saldo y vigencia del laboratorio, permisos reales, clase de instancia, horas, EBS, snapshots, red e IPv4 para estimar costo. Como orden de magnitud, una IPv4 pública a US$0,005/h supone US$3,65 por 730 h, antes de cómputo, almacenamiento y tráfico. Planificar una ventana corta de demo y retiro de los recursos facturables al cierre. Evitar compromisos mensuales o suponer créditos, GPU, IAM o persistencia de recursos sin verificar el laboratorio. [Precios EC2](https://aws.amazon.com/ec2/pricing/on-demand/) · [Precios VPC](https://aws.amazon.com/vpc/pricing/).
