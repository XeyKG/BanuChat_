## Reconstrucción local reproducible

1. Usar una copia de `data/synthetic` del commit aprobado. Si el lector seguro detecta cambios de metadatos en OneDrive, extraer `git archive --format=zip --output=<archivo-local> HEAD data/synthetic` fuera de OneDrive y fijar `BANUCHAT_SYNTHETIC_ROOT` a esa copia. El primer preflight en OneDrive falló con `SOURCE_REJECTED: read`. La copia de Git pasó el preflight existente sin relajar sus reglas.
2. Usar un PostgreSQL local de origen con v1 lista y sus vectores históricos, o un snapshot de esa release con hash y custodia verificados. Con `PGHOST=127.0.0.1`, `PGPORT`, `PGDATABASE`, `PGUSER` y credencial local del operador, ejecutar `node --import ./backend/rag/node_modules/tsx/dist/loader.mjs infra/db/cloud-01b/local-v1.mjs export <archivo-privado> <uuid-v1>`. Requiere el manifiesto v1 exacto y verifica completitud SQL, archivos y derivados. Exporta 13 tablas mediante lista positiva y un solo UUID de release, sin auth ni conversaciones. Conserva vectores, metadatos de configuración e identidad de generación.
3. Crear un clúster pgvector desechable, exclusivo, con base `banuchat_cloud01a`, puerto loopback y roles independientes. Tras verificar el contenedor y su puerto, apuntar las variables locales a ese clúster y ejecutar el mismo comando con `restore <archivo-privado> <sha256>`. La receta aplica 001, repuebla una transacción con las restricciones habilitadas y promueve con `publish_release`. Los hashes de contenido y los identificadores se preservan. El timestamp de validación corresponde a la nueva publicación. Un fallo al cargar revierte las filas y deja el esquema inicial para inspección. El script exige un esquema inicial vacío al volver a ejecutar.
4. En psql del clúster aislado, ejecutar [`local-auth.sql`](../../infra/db/cloud-01b/local-auth.sql) con `-X -f` y continuar en la misma conexión con `-f -` para el SQL emitido por `node infra/db/cloud-01a/build-successor.mjs`. El script recibe `BANUCHAT_LAB_RUNTIME_PASSWORD`, `BANUCHAT_LAB_PROVISION_PASSWORD` y `BANUCHAT_LAB_DEPLOYMENT` por el entorno del proceso psql. Si se usa Docker, copiar los SQL de `infra/db` al contenedor nuevo con su estructura relativa y pasar solo los nombres de las variables por `docker exec -e`. El bootstrap comprueba que el clúster sea dedicado antes de tocar ACL de las bases locales. Generar también el fixture físico con `node infra/db/cloud-01a/fixtures.mjs` y conservar sus bytes fuera de Git como `profiles/cloud-01a-2.json`.
5. Ejecutar `verify-vectors.sql` y [`local-inventory.sql`](../../infra/db/cloud-01b/local-inventory.sql) como verificador local. Guardar huellas en privado. Para pruebas funcionales, usar el aprovisionador y administrador actuales y los cuatro casos de login de CLOUD-01A.2. `verify-students.sql` acepta los tokens por entorno. Restaurar un dump custom en otro clúster con los roles ya creados y comparar las huellas antes de realizar logins, que modifican el estado de sesiones. El arnés de este incremento reproduce la base y la publicación. El ensayo de login, RAG y backup completo de la sucesora es evidencia histórica de CLOUD-01A.3.

La generación documental desde cero requiere Ollama y memoria para el contexto aprobado de 32768. CLOUD-01A.3 falló allí por falta de CUDA. El procedimiento de copia necesita un v1 preexistente verificable y no invoca generación. Se conserva la receta Ollama `qwen3-embedding:0.6b`, 1024 dimensiones y coseno.

## Transferencia y reversión propuestas

1. **Manual antes de ejecutar.** Confirmar referencia y región, autenticación TLS, alcance del proyecto, disponibilidad de pgvector y esquema efectivo, conectividad, roles y Data API. Preparar un inventario de ACL y dependencias equivalente al local. Exigir autorización de CLOUD-01B.1 y mantener la API cloud fuera de servicio durante la restauración.
2. **Automatizable con origen congelado.** Capturar un snapshot consistente solo de los objetos del inventario y registrar SHA-256 del dump, manifiestos, archivos y huellas por tabla. Mantener estructura de las 36 tablas. Llevar corpus y tablas académicas completas, más cuentas sintéticas, sus verificadores aprobados, bindings, grants y conversaciones/citas de prueba cuya custodia esté autorizada. Dejar vacíos en el destino sesiones, refresh, resets, contactos y flujos de recuperación, rate limits y eventos operativos. Los usuarios vuelven a iniciar sesión. Las credenciales de conexión se aprovisionan por separado. Comparar primero en clúster descartable. Registrar conteos previstos y diferencias intencionales de `runtime_scope` y tablas transitorias.
3. **Automatizable después de autorización.** Instalar o verificar extensión y propietarios manualmente según permisos del proveedor, aplicar el DDL adaptado y restaurar en orden de dependencias. Usar una transacción para la carga y `ON_ERROR_STOP`/ `--exit-on-error`. Verificar claves foráneas validadas y ausencia de filas huérfanas. Comprobar 2 releases, 120 vectores de 1024 dimensiones, 32 estudiantes y 62 intentos, hash del fixture, huellas de tablas durables y ACL. Probar login legado y U+8, progreso e historial, acceso cruzado denegado, lectura académica por sesión y retrieval/citas equivalentes. El snapshot ensayado tenía cero citas persistidas, por lo que se requiere crear y restaurar al menos un turno citado sintético para verificar la preservación de filas de citas.
4. **Reversión.** Mantener la referencia local y su último respaldo verificable. Ante una discrepancia previa al corte, conservar el runtime local y no habilitar tráfico hacia la base administrada. Tras un corte futuro, pausar escrituras antes de revertir el perfil de conexión, conservar evidencia remota y conciliar mensajes escritos en cloud con una decisión explícita antes de reanudar escrituras locales.
