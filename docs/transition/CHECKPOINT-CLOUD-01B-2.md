# CHECKPOINT BANUCHAT — CLOUD-01B.2

12 de noviembre de 2026. Base Git `main` en `b9c3b1b`, árbol inicialmente limpio. **Citas persistidas y restauradas en PostgreSQL 17.10 y pgvector 0.8.2.** El destino observado en CLOUD-01B.1 usa PostgreSQL 17.11. La conexión administrada sigue pendiente de ensayo.

## Decisión de implementación

Se revisaron CLOUD-01B.0/1, el inicio de la API, `PgAuthStore.assertRuntime`, las migraciones 001 y 006–010, `SECURITY DEFINER`, las consultas vectoriales y los scripts de publicación, inventario y asociación del despliegue. Las migraciones históricas se conservan. La 009 sigue fuera del flujo de transferencia y el formato dual del UID se preserva en el esquema publicado.

- `BANUCHAT_AUTH_POSTGRES_PROFILE=managed` activa el perfil sintético v2, con base `postgres`, puerto 5432, referencia de proyecto explícita y host de conexión directa o pooler de sesión de Supabase. El pooler exige sufijo de proyecto en el usuario. La API exige CA local y validación de hostname por el cliente TLS. Su escucha HTTP sigue en loopback. Los perfiles local, CCD, unificado y piloto mantienen sus guardas. El modo administrado se probó en la composición real de la API con un pool local de laboratorio. El arranque de producción con TLS, el endpoint y los parámetros aceptados por Supavisor quedan pendientes.
- El guard usa el rol efectivo de una conexión de login. Solo tolera `TEMP` en la base de aplicación si viene de `PUBLIC`, sin concesión directa, y `CONNECT` por `PUBLIC` a `template1` si es realmente plantilla, no pertenece al rol y el rol carece allí de CREATE y TEMP. La excepción refleja el preflight. Se rechazan otras bases conectables, membresías, roles elevados, propiedad de objetos, CREATE en esquemas persistentes, escritura directa al corpus y acceso directo a datos académicos. Mantener `pg_temp` al final del `search_path` de funciones privilegiadas y nombres de objetos calificados es parte del modelo de seguridad. Antes del corte, confirmar que `template1` sigue siendo una plantilla sin datos de aplicación accesibles.
- Se conserva `runtime_scope` como comprobación de nombre de base y UUID de despliegue. El aprovisionador y el administrador de contraseñas siguen siendo herramientas locales con sus guardas estrictas. Esta receta migra verificadores sintéticos previamente aprobados y crea sesiones nuevas tras iniciar sesión. Habilitar aprovisionamiento contra una base administrada requeriría validar por separado sus permisos y modo de operación.
- Las referencias de ingesta, MCP y API al vector están calificadas con `public`. El delta propone instalar y verificar pgvector 0.8.2 de forma controlada. La ruta ejecutable del backend de este incremento utiliza `public.vector` y el preflight rechaza otro esquema. Si Supabase instala en `extensions`, preparar y probar una adaptación dirigida de 001/010 y del DDL del dump, de los casts y firmas en API/MCP, y de las funciones y operadores de ingesta si se habilita allí. No sustituir globalmente `public`. Hasta verificar esa ruta, detener la transferencia si el esquema difiere. [Extensiones en Supabase](https://supabase.com/docs/guides/database/extensions).

### Repetición en PostgreSQL 17

Tras restablecerse Internet, se descargó `pgvector/pgvector:0.8.2-pg17` con digest `sha256:feb68f4f15446397d8cac7f4fe48fe4586de83160d1fc48b46283312d1a33966`. Se ejecutó el ensayo en dos contenedores nuevos con PostgreSQL **17.10** y pgvector **0.8.2** en `public`, `banuchat-cloud01b2-pg17-source` (loopback 55479) y `banuchat-cloud01b2-pg17-restore` (loopback 55480).

- Pasaron `pg17-vector.preflight.sql` y `pg17-vector.verify.sql` en ambos destinos. Se observaron dos releases de 60 vectores cada una, con la misma huella vectorial del ensayo PG16.
- El rol de aplicación pasó la comprobación administrada con las concesiones de `PUBLIC`. Se rechazaron las doce configuraciones inseguras del arnés, incluida TEMP sobre `template1`. El ensayo de advisory lock con dos conexiones pasó en ambos destinos.
- La API generó y persistió un turno nuevo con **cinco citas**. El respaldo custom de los tres esquemas medía **898472 bytes**, SHA-256 `9e239ecbd9e0460d177af835de98059457381af5961b466f316aaa7e106dfffc`. Después de restaurar y asociar un UUID de despliegue nuevo, se observaron cero sesiones, cero refresh tokens y cinco citas antes del login.
- En ambos destinos pasó el login, el progreso, el acceso académico por sesión, la recuperación de citas y la descarga de artefactos con su hash esperado. Una segunda cuenta recibió 404 para la conversación. La huella de referencias y contenido coincidió en origen y restauración con SHA-256 `cc26f6da21dfca33fe063c296a79af8501637042da14fba306568e954a5cfbdb`.

El ensayo cubre PostgreSQL major 17 y pgvector 0.8.2 en `public`. Quedan por comprobar el entorno administrado 17.11, la conexión con CA y hostname, los permisos del proveedor y, si se requiere, la variante con pgvector en `extensions`.
